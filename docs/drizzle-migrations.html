Drizzle schema migrations

How sndbnk owns its SQLite schema with Drizzle Kit: generate SQL, review it, apply it with Bun, and keep production data safe.

1. Mental model 2. Commands 3. Everyday workflow 4. Risk levels & production checklist 5. Why Bun has its own migrate script 6. If you know Django 7. Files that matter

1. Mental model

sndbnk is codebase-first. The Drizzle schema in src/lib/server/db/schema.js is the source of truth. Drizzle Kit diffs that schema against the last snapshot and writes SQL migration files under drizzle/. Those files are committed and applied in order.

Tool Role Use when
db:generate Diff schema → SQL file + snapshot Every schema change you intend to ship
db:migrate Apply pending SQL via Bun Local verify + every production deploy
db:backup Consistent SQLite snapshot (VACUUM INTO), keep last 14 Before production-affecting migrations
nuke Wipe DB + media + backups, remigrate Early-dev full reset (typed confirmation)
db:push:kit Push schema with no migration files Local throwaway prototyping only
db:push Retired Do not use — exits with instructions
One source of truth Do not hand-maintain a parallel DDL script. Edit schema.js, generate, review the SQL, migrate. Auth tables still come from bun run auth:schema, then generate if the Drizzle shape changed.

2. Commands

# after editing schema.js (and auth.schema if needed)
bun run db:generate

# optional name
bun x drizzle-kit generate --name add-track-mood

# review the new drizzle/000N_*.sql file, then apply
bun run db:backup          # especially before prod-shaped DBs
bun run db:migrate

# browse data locally (Node / better-sqlite3)
bun run db:studio

# full wipe + fresh migrate (type "nuke" to confirm)
bun run nuke

Deploy on Lightsail runs db:backup (when the DB file exists) then db:migrate before bun run build.

3. Everyday workflow

1
Edit the schema

Change tables in src/lib/server/db/schema.js. For better-auth columns, regenerate with bun run auth:schema && bun run format first.

2
Generate SQL

bun run db:generate writes drizzle/000N_name.sql plus a snapshot under drizzle/meta/. Commit both with the schema change.

3
Read the SQL like a PR

Watch for drop/recreate disguised as a rename, NOT NULL without a default, or data-destroying type changes. Edit the SQL by hand when the generator guesses wrong — then keep the snapshot consistent by not regenerating over a hand-tuned file without care.

4
Apply locally

bun run db:migrate, then exercise the surface with bun run dev.

5
Ship

Merge to main. Deploy backs up SQLite, migrates, builds, restarts. For destructive or data-rewriting changes, do the human checklist below first.

Data backfills

Schema DDL belongs in generated (or carefully edited) migration SQL. Idempotent seeds that must run every deploy (plan tiers, grandfathered subscription status) live at the end of scripts/migrate-sqlite.js. One-off data rewrites should be a dedicated SQL migration (drizzle-kit generate --custom --name …) so they run once and are recorded in __drizzle_migrations.

4. Risk levels & production checklist

Change Risk Notes
Add nullable column / new table / new index Low Usual path: generate → review → migrate → deploy
Add NOT NULL column Medium SQLite needs a default (or backfill strategy). Prefer nullable first.
Rename column/table Medium Generator may emit drop+add. Confirm rename SQL or do a multi-step expand/contract.
Drop column/table, change type, destroy rows High Explicit backup + human review before merge to main.
Your side before a high-risk production change
  1. Confirm the generated SQL is exactly what you intend.
  2. Take an extra backup (deploy already runs db:backup, but keep a known-good copy you can restore by hand): 
    ssh ubuntu@sndbnk.com
cd /var/www/sndbnk
set -a && source .env && set +a
bun run db:backup
ls -lt backups | head
  3. Merge and watch the deploy job apply migrations before the service restart.
  4. Smoke-test the affected queries. If something is wrong, stop deploys and restore the backups/ copy over DATABASE_URL (and sidecars) before retrying.

5. Why Bun has its own migrate script

Runtime uses bun:sqlite. Drizzle Kit’s CLI migrate/push/studio path loads better-sqlite3, which Bun cannot open. So:

  • Generate with Drizzle Kit (bun run db:generate) — reads schema files, no native driver needed.
  • Migrate with scripts/migrate-sqlite.js using drizzle-orm/bun-sqlite/migrator.
  • Studio / kit push run under Node via node ./node_modules/drizzle-kit/bin.cjs ….

Existing production databases created before this folder existed are cut over safely: if app tables already exist and __drizzle_migrations is empty, the migrate script records 0000_baseline as applied without re-running its CREATE TABLE statements, then applies any newer migrations.

6. If you know Django

Same job, different nouns — not a Django port:

Django sndbnk / Drizzle
models.py src/lib/server/db/schema.js
makemigrations bun run db:generate
Review migration file Review drizzle/000N_*.sql
migrate bun run db:migrate
django_migrations table __drizzle_migrations
RunPython / data migration Custom SQL migration, or idempotent seed in migrate script
Autodetector rename prompts Drizzle Kit rename prompts / hand-edit SQL when wrong
